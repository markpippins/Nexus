## 1. Policy-First, UI-Second — TypeSpec Drives UI Projections
**Status:** `Agreed`

### Architectural Intent
Define a policy-first, UI-second approach where a model (TypeSpec) drives UI projections, decoupling operational logic from the display. TypeSpec becomes the canonical contract for downstream consumers: automation, self-composing UIs, and simulations. EA/bureaucratic tools become TypeSpec factories — the substrate is a knowledge backbone generated by EA tools, from which purpose-built tools draw specific slices. The emitter enforces best practices (layout rules, caching strategies) while the substrate dictates structure.

### Requirements & Acceptance Criteria
- [ ] Policy-first: TypeSpec model drives UI projections

- [ ] EA tools as TypeSpec factories — generate substrate
- [ ] Emitter enforces best practices: layout rules, caching

## 2. Deterministic UI over Dynamic AI-Generated Forms
**Status:** `Agreed`

### Architectural Intent
Prefer deterministic, predictable UIs that respect muscle memory over dynamic AI-generated forms that might sacrifice consistency for novelty. UI implementation specifics (JSX/Vaadin) are separate from the TypeSpec-driven substrate. The emitter enforces layout rules and caching strategies while the substrate dictates structure. This enables policy-driven UI composition where the system can project different UIs from the same contract without sacrificing user predictability.

### Requirements & Acceptance Criteria
- [ ] Deterministic UIs > dynamic AI-generated forms
- [ ] Muscle memory and consistency over novelty
- [ ] UI implementation (JSX/Vaadin) separate from TypeSpec substrate
- [ ] Emitter enforces layout rules and caching strategies
- [ ] Policy-driven UI composition from canonical contracts
