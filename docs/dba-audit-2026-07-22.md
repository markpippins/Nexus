## CRITICAL

### 1. Conduit event-state projection is not holding

**Claimed guarantee:** `conduit.work_request_events` is the append-only event ledger, and `conduit.work_request_state` is the maintained current-state projection. Source migration `nexus/typescript/conduit-mcp/migrations/016-event-sourcing-foundation.sql` says only state transition events mutate current state through a trigger, and migration `033-conduit-schema-fixes.sql` says `check_projection_drift()` provides non-destructive replay comparison.

**Actually true now:** the live database has `31` rows in `conduit.work_request_events`, `0` rows in `conduit.work_request_state`, no non-internal triggers in schema `conduit`, and no `conduit.check_projection_drift(uuid)` function. A direct trigger scan returned no conduit trigger bindings at all. The trigger functions still exist as unattached code:

- `conduit.enforce_state_transition`
- `conduit.update_work_request_state`
- `conduit.notify_work_request_event`

**How verified:**

- `select count(*) from conduit.work_request_state;` -> `0`
- `select count(*) from conduit.work_request_events;` -> `31`
- trigger scan for `n.nspname='conduit'` -> no rows
- `conduit.check_projection_drift(s.work_request_id)` -> `ERROR: function conduit.check_projection_drift(uuid) does not exist`
- migration ledger shows conduit schema versions through `35`, but the live catalog does not contain the drift function described by source file `nexus/typescript/conduit-mcp/migrations/033-conduit-schema-fixes.sql`

**Blast radius:** anything reading `conduit.work_request_state`, relying on database-level state transition rejection, or relying on `kernel_transition_committed` notification from conduit events is reading an unmaintained or silent path. The database contains event facts but not the promised current-state projection.

## GAP

### 1. Cascade notification delivery is not durably observable

**Claimed guarantee:** database events are bridged through `pg_notify` to NATS by subscriber processes. Source file `nexus/python/cascade/obs_subscriber.py` listens on `peb_governance_event_created`, `vision_lifecycle_event_created`, `open_question_answered`, and `open_question_resolved`, then publishes CanonicalEnvelopes.

**Actually true now:** `cascade.nats_publish_log` exists but contains `0` rows. Docker shows NATS running, but the Nexus service status check reports `cascade-kernel-subscriber.service` and `cascade-obs-subscriber.service` inactive. `pg_notify` is not durable; if no subscriber is listening at commit time, the notification is lost.

**How verified:**

- `cascade.nats_publish_log` columns: `id`, `event_id`, `subject`, `published_at`, `status`, `error_message`
- `select count(*) from cascade.nats_publish_log;` -> `0`
- service status reported both cascade subscriber services inactive

**Risk:** downstream systems can miss real database events with no database error and no publish-log evidence. This is a gap even where the table-level triggers are correctly attached.

### 2. Open-question resolved notification has NULL-sensitive trigger logic

**Claimed guarantee:** `nebula.notify_open_question_event()` fires `open_question_resolved` when an open question transitions to `RESOLVED`.

**Actually true now:** the trigger is attached, and current data is clean: `165 OPEN`, `4 RESOLVED`, no `NULL` statuses, and all resolved rows have `resolved_at` and `resolved_by`. However, source `nexus/sql/V048__open_question_notify_trigger.sql` uses `NEW.status = 'RESOLVED' AND OLD.status != 'RESOLVED'`. In PostgreSQL, `OLD.status != 'RESOLVED'` is not true when `OLD.status` is `NULL`, so a future `NULL -> RESOLVED` transition would skip the notification.

**How verified:**

- trigger exists: `trg_notify_open_question_event AFTER UPDATE ON nebula.open_questions`
- current data has no null statuses
- trigger source uses the nullable comparison form

**Risk:** no active data corruption was found, but the guarantee depends on the `status NOT NULL` invariant remaining true forever. The trigger should use `OLD.status IS DISTINCT FROM 'RESOLVED'`.

### 3. Execution receipts are mutable despite being described as immutable evidence

**Claimed guarantee:** `execution.receipts` are immutable evidence produced by Execution Authority and consumed by Kernel.

**Actually true now:** the table has primary-key and foreign-key constraints only. There is no trigger preventing `UPDATE` or `DELETE`, no controlled vocabulary constraint for `type`, and the current database role has `INSERT`, `UPDATE`, and `DELETE` privileges on `execution.receipts`.

**How verified:**

- constraints on `execution.receipts`: `receipts_pkey`, `receipts_attempt_id_fkey`, `receipts_request_id_fkey`
- `has_table_privilege(current_user,'execution.receipts','insert/update/delete')` -> `true/true/true`
- current data is clean but convention-bound: receipt `type` values include the expected pipeline/execution values, with one `EXECUTION_COMPLETE`; `agent_role` values are consistent role names.

**Risk:** receipt immutability and receipt vocabulary are application discipline, not database guarantees. A raw SQL update/delete by the app role can rewrite or remove evidence.

### 4. Source migration and live conduit catalog have diverged

**Claimed guarantee:** source migration `nexus/typescript/conduit-mcp/migrations/033-conduit-schema-fixes.sql` installs `conduit.enforce_state_transition()` and `conduit.check_projection_drift()`.

**Actually true now:** the live `conduit.schema_version` table is at version `35`, but has only columns `version`, `description`, and `applied_at`; the live database lacks `check_projection_drift`. The existing `conduit.enforce_state_transition()` function body is an older NULL-sensitive version, not the newer source definition that uses JSONB key-existence (`NEW.payload ? 'new_state'`).

**How verified:**

- `select * from conduit.schema_version order by version;` returned versions `1..35`
- live function body begins with `IF NEW.event_type != 'STATE.TRANSITION_COMMITTED'` and an `EXISTS` comparison against `NEW.payload->>'new_state'`
- source migration `033-conduit-schema-fixes.sql` defines different trigger logic and a new drift function

**Risk:** source says the fix exists; the database does not. Operators cannot infer live guarantees from the checked-in SQL migration folder without also checking the actual catalog.

## DRIFT

### 1. Receipt `type` is a free-text controlled vocabulary

**Claimed guarantee:** receipt rows encode stable evidence types.

**Actually true now:** current values are coherent, but `execution.receipts.type` is plain `TEXT NOT NULL`; there is no `CHECK`, enum, or lookup table. Current distinct values:

- `PLAN_CREATE` 390
- `BLOCK` 303
- `REVIEW_REJECT` 293
- `IMPLEMENTATION` 173
- `REVIEW_PASS` 100
- `REQUEUED` 70
- `PROPOSED` 58
- `API_LIMIT` 55
- `PLANNING` 54
- `CANCELLED` 38
- `HOLD` 20
- `REVIEW` 3
- `EXECUTION_COMPLETE` 1

**Risk:** no near-duplicate was observed in the current values, but the column can drift silently.

### 2. Legacy trigger functions remain in the catalog without attachments

The broad trigger attachment audit found many unattached trigger-returning functions in `nebula` and `vision`. Some are likely residue from view-trigger renames or SCD4 migrations: for example, active `vision.lifecycle_events` triggers call `lifecycle_events_view_*_trigger`, while older `vision.lifecycle_events_*_trigger` functions remain unattached.

This is not itself a defect for every function, but it is drift in the operational surface. Unattached trigger functions with governance names should either be documented as historical residue or removed in a controlled cleanup.

## OBSERVATION

### 1. The reported `create_plan` `ON CONFLICT` incident is not explained by the current `implementation_plans` catalog

Assembly contains an open issue reporting `conduit-mcp create_plan` failing with `no unique or exclusion constraint matching the ON CONFLICT specification`. Source `nexus/typescript/conduit-mcp/src/db.ts` uses:

```sql
ON CONFLICT (plan_number) WHERE plan_number IS NOT NULL DO UPDATE
```

The live catalog now has:

- `implementation_plans_pkey PRIMARY KEY (id)`
- `uq_implementation_plans_plan_number UNIQUE (plan_number)`

That full unique constraint should satisfy `ON CONFLICT (plan_number)`; it does not explain the reported error by itself. Possibilities include a stale service process, a different database target during the failure, a previous catalog state before `V044`, or another `ON CONFLICT` path.

### 2. Kernel receipt enforcement appears improved

Previous Assembly discussion called out `kernel.receipt` as a sole-write-surface gap. The live catalog now has `trg_authorize_receipt BEFORE INSERT ON kernel.receipt`, alongside `trg_authorize_transition` and `trg_notify_transition` on `kernel.transition_event`.

This does not prove all kernel guarantees, but the specific receipt-insert enforcement gap appears addressed in the live catalog.

### 3. Execution lease TTL data is clean right now

`execution.leases` contains `321 RELEASED` leases and `0 ACTIVE` leases. There are no active expired leases at audit time. The TTL surface should still be checked when active execution load exists, because this run did not exercise an active lease.
