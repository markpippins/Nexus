ScopeThis document defines how the initial WRP artifact set is ingested into Nebula:- `docs/wrp/wrp-v1-protocol.md`- `docs/wrp/wrp-v1_1-dag-model-and-compilation-pipeline.md`- `docs/wrp/wrp-v1_2-execution-traversal-engine.md`- `docs/wrp/wrp-migration-plan.md`The projection pipeline transforms those markdown documents into:- `NebulaArtifact` records- `NebulaSection` records- `NebulaChunk` records- `NebulaCrossReference` records- optional execution links to Conduit plans and receiptsThis document governs **projection behavior**, not authoring style. It specifies how Nebula should interpret WRP documents that already exist.---# 2. Projection ObjectivesThe projection pipeline MUST produce a graph that supports:1. **role-shaped retrieval**- Builder sees implementation-oriented chunks- Architect sees subsystem and rationale chunks- Inspector sees invariants, migration rules, and protocol constraints- Explorer sees rationale, open questions, and broader cross-artifact context2. **artifact-level identity**- each WRP document projects to a stable `NebulaArtifact`- each section and chunk receives stable identifiers3. **chunk-level stratification**- level assignment is done at chunk level, not only document level- a single document may yield L1, L2, and L3 chunks4. **cross-reference graph construction**- explicit and inferred relationships between chunks, sections, and artifacts are materialized into Nebula edges5. **Conduit interoperability**- artifacts and chunks may link to Conduit plans, execution receipts, or migration records where applicable---# 3. Projection Pipeline OverviewProjection MUST proceed in the following stages:1. **Artifact Resolution**- map source markdown file to known `NebulaArtifact`- create artifact if missing and bootstrap mode permits creation2. **Markdown Parsing**- parse headings, lists, paragraphs, tables, fenced code blocks, block quotes3. **Section Construction**- create ordered `NebulaSection` records from heading hierarchy4. **Chunk Segmentation**- split section bodies into semantically coherent `NebulaChunk` units5. **Chunk Classification**- assign:- `level`- `chunkKind`- `normativeStrength`- `status`- optional tags / concepts6. **Cross-Reference Extraction**- emit explicit and inferred edges among artifacts, sections, and chunks7. **Execution Link Attachment**- attach Conduit plan or receipt links where metadata exists8. **Persistence / Upsert**- write artifact/section/chunk/xref records using stable ids and idempotent upsert semantics---# 4. Source Artifact Mapping## 4.1 Canonical artifact bindingsThe following markdown files MUST map to these canonical artifacts:| Source file | Artifact ID | Artifact Key ||---|---|---|| `docs/wrp/wrp-v1-protocol.md` | `wrp:artifact/wrp-v1-protocol` | `wrp-v1-protocol` || `docs/wrp/wrp-v1_1-dag-model-and-compilation-pipeline.md` | `wrp:artifact/wrp-v1_1-dag` | `wrp-v1_1-dag` || `docs/wrp/wrp-v1_2-execution-traversal-engine.md` | `wrp:artifact/wrp-v1_2-traversal` | `wrp-v1_2-traversal` || `docs/wrp/wrp-migration-plan.md` | `wrp:artifact/wrp-migration-plan` | `wrp-migration-plan` |## 4.2 Artifact creation policyIf a source document is encountered that is not already present in the bootstrap registry:- projection MUST fail by default in strict mode- projection MAY create a new `NebulaArtifact` in permissive mode if:- artifact family can be inferred- artifact key is stable- a document path is availableStrict mode is the default for WRP v1 bootstrap ingestion.---# 5. Section Construction Rules## 5.1 Heading-based section boundariesMarkdown headings define section boundaries.- `#` = document root title (not a `NebulaSection` unless explicitly configured)- `##` = top-level section- `###` = child section of nearest preceding `##`- `####` and below = nested section nodes OR local substructure depending on depth policyDefault policy:- persist `##` and `###` as `NebulaSection`- treat `####+` as internal segmentation hints unless a document is unusually deep and preservation is requested## 5.2 Stable section identifiersEach section MUST receive a stable `sectionKey` derived from:- artifact key- normalized heading path### normalization rules- lowercase- spaces → `-`- strip punctuation except internal hyphen separators- collapse repeated separators- include ancestry path for nested sections### examplesDocument:- `wrp-v1-protocol`Heading:- `## Identity and Versioning`Section key:- `wrp-v1-protocol.identity-and-versioning`Nested heading:- `## Execution Semantics`- `### Receipts`Section key:- `wrp-v1-protocol.execution-semantics.receipts`## 5.3 Section orderingEach section MUST store:- `ordinal` within artifact- `headingLevel`- `parentSectionId` if nestedOrder is derived from source markdown order and MUST be stable across re-import if heading order is unchanged.---# 6. Chunk Segmentation RulesSections are often too coarse to retrieve effectively. Each section MUST be segmented into one or more `NebulaChunk` units.## 6.1 Chunking principleA chunk MUST represent **one dominant semantic purpose**.Do not mix the following in a single chunk unless they are inseparable and short:- protocol rule + migration checklist- rationale + normative invariant- algorithm + historical commentary- open question + implementation task list## 6.2 Primary chunk boundariesWithin a section, start a new chunk when any of the following occurs:1. **normative mode switch**- descriptive exposition changes into explicit requirements- requirements change into rationale or migration guidance2. **semantic subtype switch**- protocol semantics → data model- data model → algorithm- rationale → open questions- migration steps → compatibility constraints3. **structural block boundary**- fenced code block introducing a new implementation concern- numbered migration checklist- table encoding a model or mapping- quoted rule / invariant block4. **topic pivot**- paragraph group changes subject materially even within same heading## 6.3 Secondary chunk boundariesThe projector SHOULD split large chunks when:- chunk text exceeds configured token threshold- chunk contains more than one independent invariant- chunk contains more than one migration step cluster- chunk interleaves prose and code examples in a way that harms retrieval specificity## 6.4 Default chunk size guidanceTarget chunk size:- **preferred:** 150–450 tokens- **acceptable:** 80–700 tokensThe projector SHOULD avoid:- micro-chunks that contain only one sentence unless it is a high-value invariant- mega-chunks that contain an entire section with mixed concerns---# 7. Chunk ClassificationEach chunk MUST be assigned:- `level`- `chunkKind`- `normativeStrength`- `status`- optional concept tags---# 8. Level Assignment RulesLevels represent the abstraction stratum of the chunk itself, not the artifact as a whole.## 8.1 L1 — implementation / operational detailAssign `nebula:L1` when a chunk is primarily about:- file/module/class layout- API signatures or field-level request/response shapes- schema fields and exact JSON examples- traversal step logic in implementation form- migration task checklists- compatibility adapters and rollout steps- concrete validation checks- code-generation or compilation pass details- exact Conduit integration mechanics### examples- “add `level` to `nebula_artifact` and `nebula_cross_reference`”- “compiler emits `ExecutionReceipt` nodes with parent cursor ids”- “Phase 2 migration sequence: dual-write old plan registry and WRP graph”## 8.2 L2 — subsystem semantics / formal system behaviorAssign `nebula:L2` when a chunk is primarily about:- protocol semantics- DAG semantics- traversal semantics- formal lifecycle rules- graph invariants- execution contracts- state transition rules- artifact relationship semantics- chunk schema semantics### examples- “a WRP request compiles into a DAG whose nodes are execution units”- “receipts are immutable records of execution outcomes”- “Traversal must not execute a node whose predecessors are incomplete”## 8.3 L3 — architectural rationale / migration strategy / design tradeoffAssign `nebula:L3` when a chunk is primarily about:- why the protocol is structured this way- tradeoffs among alternative models- migration sequencing and rollout strategy- compatibility philosophy- boundary decisions between Nebula / Conduit / runtime- architectural decomposition rationale### examples- “Migration is staged so legacy workflows can coexist during cutover”- “Traversal remains separate from protocol formalization to preserve replaceability”- “Chunk-level levels are necessary because one document mixes implementation and rationale”## 8.4 L4 — doctrine / meta-ontology / worldviewAssign `nebula:L4` when a chunk is primarily about:- universal methodology- ontology-first doctrine- role philosophy- persistent engineering brain rules- meta-rules governing how artifacts should be interpreted across domainsWRP documents will rarely contain L4 chunks, but the projector MUST allow them if they appear.## 8.5 Tie-breaking ruleIf a chunk mixes levels, assign the level of the **dominant actionable purpose**.Tie-break priority:- if implementation instructions are present and operationally central → `L1`- else if formal subsystem semantics dominate → `L2`- else if rationale/tradeoff dominates → `L3`- else doctrine/meta → `L4`---# 9. Chunk Kind Classification RulesEach chunk MUST be assigned a `chunkKind`.## 9.1 Core chunk kindsThe WRP projector MUST support at least the following kinds:- `OVERVIEW`- `DEFINITION`- `PROTOCOL_RULE`- `DATA_MODEL`- `ALGORITHM`- `INVARIANT`- `RATIONALE`- `MIGRATION_STEP`- `ACCEPTANCE_CRITERIA`- `OPEN_QUESTION`- `EXAMPLE`- `IMPLEMENTATION_NOTE`## 9.2 Classification heuristics### `OVERVIEW`Use for:- section introductions- high-level summaries of a subsystem or artifact### `DEFINITION`Use for:- explicit term definitions- identity/lifecycle terminology- conceptual type descriptions not yet prescribing behavior### `PROTOCOL_RULE`Use for:- request/response semantics- protocol-level must/should rules- lifecycle constraints expressed as protocol behavior### `DATA_MODEL`Use for:- node/edge structures- fields, schemas, object model mappings- compilation or receipt data shapes### `ALGORITHM`Use for:- traversal order- graph compilation passes- validation procedures- deterministic execution logic### `INVARIANT`Use for:- statements that must always hold across valid WRP state- acyclicity, immutability, uniqueness, ordering guarantees### `RATIONALE`Use for:- “why” explanations- architectural tradeoffs- boundary explanations- decomposition reasoning### `MIGRATION_STEP`Use for:- rollout sequencing- compatibility tasks- backfill / cutover steps- staged adoption instructions### `ACCEPTANCE_CRITERIA`Use for:- explicit conditions for completion or correctness- verification checklist items### `OPEN_QUESTION`Use for:- unresolved design questions- TODO architecture decisions- future investigation points### `EXAMPLE`Use for:- worked examples- sample requests / DAG shapes / traversal traces### `IMPLEMENTATION_NOTE`Use for:- code-facing notes- file layout guidance- “do this in the importer/compiler/runtime” instructions## 9.3 Multi-label ruleA chunk SHOULD have one primary `chunkKind`.A secondary tag list MAY be attached separately if a chunk straddles multiple concerns, but retrieval ranking MUST use the primary kind.---# 10. Normative Strength ExtractionEach chunk MUST be assigned a `normativeStrength`.## 10.1 Allowed strengths- `REQUIRED`- `PROHIBITED`- `RECOMMENDED`- `INFORMATIVE`## 10.2 Extraction rules### `REQUIRED`Use when the chunk contains language such as:- must- shall- is required to- cannot be valid unless- always### `PROHIBITED`Use when the chunk contains:- must not- shall not- never- prohibited- invalid if### `RECOMMENDED`Use when the chunk contains:- should- recommended- ordinarily- preferred- expected to### `INFORMATIVE`Use when the chunk is primarily descriptive, explanatory, or exploratory and does not prescribe behavior.## 10.3 Mixed normative languageIf a chunk contains both informative explanation and a clear normative rule, the chunk SHOULD be split if possible.If not split, normative strength follows the strongest explicit rule present:- `PROHIBITED` > `REQUIRED` > `RECOMMENDED` > `INFORMATIVE`---# 11. Status AssignmentProjected chunks MUST default to `nebula:ACTIVE` unless source metadata indicates otherwise.The projector SHOULD support future status extraction for:- `DRAFT`- `ACTIVE`- `SUPERSEDED`- `DEPRECATED`Possible signals:- explicit frontmatter- “superseded by” text- migration plan status tables- artifact registry metadata---# 12. Cross-Reference ExtractionThe projector MUST extract cross-references at artifact, section, and chunk level where possible.## 12.1 Explicit artifact referencesEmit a cross-reference when a chunk explicitly mentions a known artifact key or canonical artifact title.### examples- `wrp-v1_1-dag`- `WRP Migration Plan`- `WRP v1.0 Protocol Formalization`## 12.2 Section referencesEmit a section-level cross-reference when a chunk references another section by heading name or stable section key.### examples- “see Identity and Versioning”- “as described in Execution Semantics / Receipts”## 12.3 Known concept referencesThe projector SHOULD maintain a concept lexicon for high-value WRP terms such as:- `ExecutionContext`- `ExecutionReceipt`- `WorkRequest`- `TraversalCursor`- `CompiledDag`- `MigrationPhase`- `ProtocolVersion`Mentions of these MAY emit:- concept tags- chunk-to-chunk inferred references- future concept nodes if concept projection is enabled## 12.4 Link-derived referencesMarkdown links MUST be interpreted as references and MAY become:- chunk → chunk edges if target is internal- chunk → artifact edges if target is another artifact- chunk → external source edges if external references are permitted## 12.5 Relation type inferenceDefault inferred relation types:- mentions protocol artifact semantics → `DEPENDS_ON`- migration instructions targeting another artifact → `MIGRATES`- rationale explaining why another structure must exist → `CONSTRAINS`- worked example illustrating another chunk → `EXEMPLIFIES`- open question about another artifact/section → `RAISES_QUESTION`If relation type is ambiguous, default to `REFERENCES` unless stricter inference rules are configured.---# 13.
