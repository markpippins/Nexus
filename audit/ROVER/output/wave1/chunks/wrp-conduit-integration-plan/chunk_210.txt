# 3. Design Goals

The projection and stratification model must satisfy the following goals.

## G1. Preserve long-form WRP knowledge in Nebula

The WRP packet tracked in Conduit must be represented in Nebula as durable, queryable, versioned knowledge.

## G2. Preserve execution alignment with Conduit

Nebula entries must retain enough metadata to map back to the Conduit work packet(s) that implement them.

## G3. Support role-specific retrieval

The same corpus must serve multiple retrieval surfaces:

- Builder / implementer
Builder / implementer

- Architect / planner
Architect / planner

- Inspector / validator
Inspector / validator

- Explorer / researcher
Explorer / researcher

## G4. Separate abstraction levels cleanly

Implementation details should not drown architectural reasoning, and architectural rationale should not flood implementation prompts unless explicitly requested.

## G5. Preserve explicit cross-references

Protocol rules, DAG semantics, traversal rules, migration tasks, invariants, and open questions must be linked explicitly rather than relying only on embedding similarity.

## G6. Remain compatible with the existing Nebula markdown-ingestion pipeline

This design should extend the existing markdown import / chunk / cross-reference model rather than replacing it.

# 4. Core Decision

## 4.1 Canonical rule

WRP artifacts are authored or curated as Nebula documents, then projected into Conduit as executable work packages.

Conduit may hold the immediate execution plans, but Nebula remains the authoritative architectural memory for:

- protocol definitions,
protocol definitions,

- subsystem specs,
subsystem specs,

- migration rationale,
migration rationale,

- invariants,
invariants,

- open questions,
open questions,

- design history.
design history.

## 4.2 Projection direction

There are two distinct projection paths:

### A. Authoritative knowledge projection

```
Nebula markdown/spec document    → Nebula document rows / chunks / cross references    → optional WRP artifact registration    → Conduit plan / work request generation
```

```
Nebula markdown/spec document    → Nebula document rows / chunks / cross references    → optional WRP artifact registration    → Conduit plan / work request generation
```

### B. Execution trace back-projection

```
Conduit plan / execution receipt / implementation status    → WRP artifact linkage    → Nebula document metadata updates    → cross-linked execution references
```

```
Conduit plan / execution receipt / implementation status    → WRP artifact linkage    → Nebula document metadata updates    → cross-linked execution references
```

So the system is not one-way. The long-form knowledge projects downward into executable work, and execution status projects upward into Nebula metadata and trace links.

# 10. Level Assignment Rules

## 10.1 Canonical rule

Level belongs primarily to the content node, not to the retrieval query and not to the edge.

That means:

- documents have levels,
documents have levels,

- chunks have levels,
chunks have levels,

- references may optionally have level metadata, but level is not primarily an edge property.
references may optionally have level metadata, but level is not primarily an edge property.

## 10.2 Single-primary-level rule

Every document and every chunk must haveone primary level.

This avoids ambiguous retrieval behavior and keeps filtering deterministic.

## 10.3 Mixed documents

A long document may contain sections at different abstraction levels. Therefore:

- thedocumentreceives a default or dominant level;
thedocumentreceives a default or dominant level;

- chunksmay override the document level when section content clearly belongs to a different level.
chunksmay override the document level when section content clearly belongs to a different level.

Example:

- a WRP migration document may be primarilyL3,
a WRP migration document may be primarilyL3,

- but its implementation checklist section may be chunked asL1.
but its implementation checklist section may be chunked asL1.

## 10.4 Edge neutrality rule

Cross-reference edges should belevel-neutral by default.The edge describes the relationship; the source and target nodes carry the abstraction level.
