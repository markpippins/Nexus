## 1. Core principle: one namespace, not one schema

The lookup key is the **unit name** — identical identity space to the
ratified `<UNIT>_TARGET` env convention and the systemd unit files:

```
wind-srv            → WIND_SRV_TARGET        → lookup key: wind-srv
conduit-mcp         → CONDUIT_MCP_TARGET     → lookup key: conduit-mcp
file-system-server  → FILE_SYSTEM_SERVER_TARGET → lookup key: file-system-server
```

- One logical service identity across config (env), runtime (lookup), and
  orchestration (systemd). No new naming ontology.
- **Resolution precedence:** `lookup(unit) ?? $<UNIT>_TARGET ?? localhost-default`.
  Env var stays the static default; lookup is the runtime override; dev
  fallback unchanged. Wind-ui `VITE_*` and `.env.example` keep working.
- **Failover without config churn:** cutover flips which endpoint is
  `primary`; consumers re-resolve. No redeploy, no fleet `.env` edit.

## 2. 1.1 — Canonical schema: DEFERRED (unchanged)

No forced unification of registry (:8085) vs terrain (:8084) Server/Service
shapes. `nebula.assessment_resolutions` stays the assessment-layer home.
**Nothing hinges on resolution-schema changes** (no movement there as of
2026-08-15). 1.2/1.3 deliver value without schema-merge risk.

## 3. 1.3 — Instance-lookup contract (the linchpin)

**Served by terrain (:8084)** — runtime/provisioning truth (`RunnableService`
68 rows, `McpServer` 14 rows, ports + healthCheckUrl). Registry (:8085)
contributes freshness (heartbeat), not location.

### Contract

```
GET /api/v1/lookup/<unit>
200 {
  "unit": "wind-srv",
  "envVar": "WIND_SRV_TARGET",
  "endpoints": [
    { "instance": "primary", "host": "10.0.1.5", "ip": "10.0.1.5", "port": 3300, "scheme": "http",
      "status": "UP", "lastHeartbeat": "2026-08-16T01:30:00Z" },
    { "instance": "failover", "host": "10.0.2.9", "ip": "10.0.2.9", "port": 3300, "scheme": "http",
      "status": "STANDBY", "lastHeartbeat": "2026-08-16T01:30:02Z" }
  ],
  "preferred": "primary"
}
404 { "unit": "wind-srv", "error": "unknown_unit" }
```

### IP-aware data model (user direction — the schema IS touched)

New additive table on terrain: **`service_endpoints`** — unit-name keyed,
IP first-class from day one (not inferred/derived):

```sql
CREATE TABLE terrain.service_endpoints (
  id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  unit           TEXT NOT NULL,               -- logical identity = <UNIT>
  instance       TEXT NOT NULL DEFAULT 'primary',  -- primary | failover
  host           TEXT NOT NULL,               -- hostname
  ip             INET NOT NULL,               -- IP address (v4/v6) — first-class
  port           INT NOT NULL,
  scheme         TEXT NOT NULL DEFAULT 'http',
  status         TEXT NOT NULL DEFAULT 'UNKNOWN',
  last_heartbeat TIMESTAMPTZ,
  UNIQUE (unit, instance)
);
```

- Seeded/synced from terrain `runnable_services` + host servers (host→ip).
  Ansible-provisioned standbys fill `failover` rows later (post container-test gate).
- Lookup: `SELECT * FROM service_endpoints WHERE unit = $1 ORDER BY instance`
  (+ status merge from registry heartbeat when present).
- Additive and backwards-compatible — no changes to existing
  `runnable_services` / `mcp_servers`.
- **Batch variant:** `GET /api/v1/lookup?units=a,b,c` mirroring the existing
  `/heartbeat/batch` pattern.
- **Credential discipline:** the lookup DTO never exposes `sysUser`/`sysPass`
  (terrain Server credential-in-schema smell, 0.2). Excluded by construction —
  hard contract clause.
- **Shape consistency:** list responses use the existing
  `{ data, meta }` pagination (0-indexed `page`, `per_page=20`).

## 4. 1.2 — Sync semantics: runtime facts flow one way

1. **Add `origin` (seed | register) provenance column** to registry services
   first — prerequisite for idempotent/reversible sync (0.4 finding: today
   origin is only inferable from `description` text).
2. **Direction: terrain (runtime truth) → registry (catalog).** Registry keeps
   the declarative catalog (frameworks, types, descriptions from seed
   untouched); terrain pushes runtime facts (up/down, port, health).
3. **Idempotent upsert keyed on unit name** — never overwrite catalog-metadata
   fields, only runtime-fact fields. Declarative catalog and runtime facts
   never fight (governance invariant).
4. **Mechanics:** reuse `POST /api/v1/registry/register` +
   `/heartbeat/batch` — a sync job walks terrain `runnable_services` and
   registers/heartbeats what is missing. Covers the Node/Python fleet that
   does not self-register (0.3 gap) without touching those services.

## 5. 1.4 — Dependency authority: RULING

**Terrain `service-dependencies` is the runtime dependency authority**
(19 rows; `sourceType/sourceId/targetType/targetId` + `criticality`; spans
runnable + MCP). The registry graph is the catalog projection. Failover
re-resolution ordering (which units re-resolve, in what order) comes from
terrain, criticality-aware. **No new dependency model** — 1.3 consumes
terrain's existing graph.
