# T25 1.2 — Origin-Column Migration Design (Registry V10)

> Architect design (opencode/big-pickle) · 2026-08-16 · R-A-2026-08-15-008 sequencing step ②
> Grounded in: `docs/t25/0.4-catalog-entry-origin-report.md`, live entity/migration reads.
> DB: MySQL (registry schema), Flyway-managed (V1–V9 in place → next is **V10**).

---

## 1. Why

The `registry.services` catalog mixes seeded (declarative, from
`service-configurations.json` / `DataInitializer`) and runtime-registered
entries (`POST /api/v1/registry/register`) with **no persistent origin
marker**. Today origin is only inferable from `description =
"External service registered via API"` and the seed JSON files — fragile
for the 1.2 sync (which must never overwrite catalog metadata with
runtime facts, and must be idempotent + reversible).

## 2. Change set

### 2.1 Flyway migration — `V10__add_origin_column_to_services.sql`

New file in `jvm/spring/service-registry/src/main/resources/db/migration/`:

```sql
-- T25 1.2: provenance marker for services catalog entries.
-- seed    = declarative, loaded from config JSON / DataInitializer (catalog truth)
-- register= created at runtime via POST /api/v1/registry/register (runtime fact)
ALTER TABLE registry.services
    ADD COLUMN origin VARCHAR(20) NOT NULL DEFAULT 'seed';

-- Backfill: entries that were runtime-registered (per the only marker
-- available before this migration) get origin='register'.
-- Match is exact and intentionally narrow — never fuzzy on description.
UPDATE registry.services
   SET origin = 'register'
 WHERE description = 'External service registered via API';

-- Guard: registration path must set origin explicitly (see 2.3).
```

- `DEFAULT 'seed'` keeps every existing seed path (DataInitializer,
  `NebulaSeedController`, SQL) working untouched — they never set the
  column and get `seed` for free.
- Backfill is one-shot, exact-match, and idempotent (Flyway runs it once).

### 2.2 Entity — `Service.java`

Add field (no behavior change; old code paths unaffected):

```java
@Column(name = "origin", length = 20)
private String origin = "seed";   // seed | register
```

Plus getter/setter. `@Column(nullable=false)` is NOT added — the DB
default covers legacy insert paths; Hibernate-level nullability would
force every constructor site to set it. (Optional hardening: add
`@Column(insertable=false)` is wrong — registration path needs to write
it; keep the plain column.)

### 2.3 Registration service — `ExternalServiceRegistrationService.java`

In `registerExternalService`, set provenance explicitly:

```java
service.setOrigin("register");
```

Placed next to `service.setDescription("External service registered via API")`
(which stays as the human-readable marker). This makes the registration
path self-describing in both columns.

## 3. What this enables (and does NOT do)

- ✅ Enables 1.2 sync: sync job (terrain → registry via
  `POST /api/v1/registry/register` + `/heartbeat/batch`) can now
  distinguish, update runtime-fact fields only, and remain idempotent
  keyed on unit name — never touching `origin='seed'` catalog metadata.
- ✅ Reversible provenance: `origin` column can be queried/reported
  (0.4 report becomes a query instead of a scan of description text).
- ❌ NOT a schema merge — no registry↔terrain table unification (1.1 stays
  deferred to `nebula.assessment_resolutions`).
- ❌ NOT the sync job itself (that is sequencing step ④).
- ❌ NOT `service_endpoints` / lookup endpoints (that is step ③, terrain-side).

## 4. Ordering note

V10 is the **first** DDL of the 1.x leg and the only registry-side change
in this leg. Steps ③ (`terrain.service_endpoints` + lookup) and ④ (sync
job) depend on it only for the sync's provenance discipline — ③ can be
built in parallel on the terrain side.

## 5. Acceptance

1. `registry.services` has `origin` column, all 69 rows populated
   (`seed` / `register`), matches the 0.4 observed mix.
2. Existing seed paths produce `origin='seed'` (regression: reseed a
   fixture, confirm).
3. `POST /api/v1/registry/register` produces `origin='register'` (manual
   test: register a scratch name, confirm column + description).
4. No behavior change to catalog API responses (entity serialization:
   `origin` may appear in `Service` JSON — verify frontends ignore
   unknown fields, or annotate `@JsonIgnore` on the getter if not).
