      - Simulate occasional failures (10% chance of rejection)

between mock → real backend:

[ ] TypeScript interfaces match backend Pydantic models field-for-field
[ ] Nullable/optional fields are consistent (null vs undefined vs omitted)
[ ] Enum values match exactly (string values, not positions)
[ ] Date format is ISO-8601 (not timestamps, not locale strings)
[ ] IDs are strings (UUIDs) once backend moves beyond int PKs
[ ] Error shapes match: { detail: string } for REST, { type: "error", ... } for WS
[ ] Pagination params/meta match (skip/limit or cursor-based)
[ ] HTTP status codes match FastAPI conventions (201 for create, etc.)

7.  MOCK-TO-REAL SERVICE REPLACEMENT ORDER
----------------------------------------------------------------------

Each backend phase should be preceded by mock services in the UI. When
the backend phase completes, replace the mock with an HTTP/WebSocket
adapter. Adapter interface pattern:

    interface WorkRequestService {
      create(intent: string, metadata?: dict): Promise<WorkRequest>;
      get(id: number): Promise<WorkRequest>;
      list(): Promise<WorkRequest[]>;
    }

    // Mock implementation (Phase 0)
    class MockWorkRequestService implements WorkRequestService { ... }

    // Real implementation (Phase 1+)
    class ApiWorkRequestService implements WorkRequestService { ... }

    // Inject via dependency injection or service locator:
    const service: WorkRequestService =
      useMock ? new MockWorkRequestService() : new ApiWorkRequestService();

This pattern allows both implementations to coexist during transition,
enabling frontend development independent of backend progress.
