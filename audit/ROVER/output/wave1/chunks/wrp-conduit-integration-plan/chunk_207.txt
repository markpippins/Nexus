PurposeThis document defines how **WRP artifacts managed through Conduit** are projected into the **Nebula knowledge graph / document corpus**, and how those artifacts are stratified by **abstraction level** so that different roles and agents can retrieve the right amount of context.The immediate goal is to support the first WRP work packet now tracked in Conduit:1. **WRP v1.0** — protocol formalization2. **WRP v1.1** — DAG data model & compilation pipeline3. **WRP v1.2** — execution traversal engine4. **WRP migration plan**These four artifacts must not remain isolated implementation plans. They must become **queryable architectural knowledge** inside Nebula so that:- builders can retrieve concrete implementation guidance,- architects can retrieve subsystem rationale and relationships,- inspectors/validators can retrieve invariants and migration constraints,- future harvests and work requests can cross-reference WRP material directly.This document therefore specifies:- the **projection model** from Conduit/WRP artifacts into Nebula;- the **`level` stratification model** for Nebula documents, chunks, and references;- the **artifact taxonomy** for WRP knowledge units;- the **retrieval policy** by role;- the **migration strategy** for the initial WRP corpus.---# 2. Design GoalsThe projection and stratification model must satisfy the following goals.G1. Preserve long-form WRP knowledge in NebulaThe WRP packet tracked in Conduit must be represented in Nebula as durable, queryable, versioned knowledge.G2. Preserve execution alignment with ConduitNebula entries must retain enough metadata to map back to the Conduit work packet(s) that implement them.G3. Support role-specific retrievalThe same corpus must serve multiple retrieval surfaces:Builder / implementerArchitect / plannerInspector / validatorExplorer / researcherG4. Separate abstraction levels cleanlyImplementation details should not drown architectural reasoning, and architectural rationale should not flood implementation prompts unless explicitly requested.G5. Preserve explicit cross-referencesProtocol rules, DAG semantics, traversal rules, migration tasks, invariants, and open questions must be linked explicitly rather than relying only on embedding similarity.G6. Remain compatible with the existing Nebula markdown-ingestion pipelineThis design should extend the existing markdown import / chunk / cross-reference model rather than replacing it.4. Core Decision4.1 Canonical ruleWRP artifacts are authored or curated as Nebula documents, then projected into Conduit as executable work packages.Conduit may hold the immediate execution plans, but Nebula remains the authoritative architectural memory for:protocol definitions,subsystem specs,migration rationale,invariants,open questions,design history.4.2 Projection directionThere are two distinct projection paths:A. Authoritative knowledge projectionNebula markdown/spec document→ Nebula document rows / chunks / cross references→ optional WRP artifact registration→ Conduit plan / work request generationB. Execution trace back-projectionConduit plan / execution receipt / implementation status→ WRP artifact linkage→ Nebula document metadata updates→ cross-linked execution referencesSo the system is not one-way. The long-form knowledge projects downward into executable work, and execution status projects upward into Nebula metadata and trace links.5. Level Stratification Model8. Rationale for Level StratificationWithout level stratification, a retrieval system operating over mixed architectural and implementation material tends to collapse the distinction between:“what the protocol means,”“how the DAG is represented,”“what code needs to change this week,”“why the migration strategy was chosen.”That leads to three recurring failures:Builders get too much theoryimplementation prompts fill with architecture prose and migration history.Architects get too much local detailsubsystem reasoning is polluted by file-level implementation instructions.Inspectors miss normative constraintsinvariants and compatibility rules are not distinguished from general descriptive prose.A level field provides a stable, queryable abstraction boundary.9. Level DefinitionsThe first version of the level system usesfour levels.Level 1 — Execution / Build Detail (L1)Concrete implementation guidance and execution-facing material.Typical content:file-level implementation tasksendpoint contractsdataclass / schema detailsmethod signaturesSQL changesacceptance criteriatest casesmigration scriptsprecise repository change instructions“do this in package X” contentPrimary consumers:BuilderConduit executorimplementation-focused coding agentsLevel 2 — Subsystem Design (L2)Subsystem mechanics and technical design for a bounded domain.Typical content:DAG node/edge semanticscompilation pipeline structuretraversal algorithm designexecution receipt structurerole-specific service boundariesstorage mappings for a specific subsystemformal state transitions inside one bounded domainPrimary consumers:Builder (secondary)ArchitectInspectorLevel 3 — Architecture / Rationale (L3)Higher-order architectural reasoning, system relationships, and design justification.Typical content:why WRP existswhy DAG compilation is separate from traversalhow Conduit, Nebula, and LOSM relatemigration philosophy and rollout strategycross-subsystem responsibilitieslong-form tradeoff analysisarchitectural invariants spanning multiple packagesPrimary consumers:ArchitectExplorerInspectorLevel 4 — Meta / Doctrine / Ontology (L4)Cross-cutting design doctrine, system philosophy, and ontology-level governance.Typical content:methodology rulesrole doctrinearchitectural constitution / invariants of invariantsontology rules for work, memory, or cognitionglobal modeling principlescross-project strategic doctrinePrimary consumers:ArchitectExplorerstrategic planner10. Level Assignment Rules10.1 Canonical ruleLevel belongs primarily to the content node, not to the retrieval query and not to the edge.That means:documents have levels,chunks have levels,references may optionally have level metadata, but level is not primarily an edge property.10.2 Single-primary-level ruleEvery document and every chunk must haveone primary level.This avoids ambiguous retrieval behavior and keeps filtering deterministic.10.3 Mixed documentsA long document may contain sections at different abstraction levels. Therefore:thedocumentreceives a default or dominant level;chunksmay override the document level when section content clearly belongs to a different level.Example:a WRP migration document may be primarilyL3,but its implementation checklist section may be chunked asL1.10.4 Edge neutrality ruleCross-reference edges should belevel-neutral by default.The edge describes the relationship; the source and target nodes carry the abstraction level.11. Recommended Level Mapping for the Initial WRP Corpus11.1 WRP v1.0 Protocol FormalizationDefault document level:L2Reasoning:it defines subsystem protocol semantics and normative message shape;it is not merely implementation detail;it is narrower than whole-system doctrine.Typical chunk-level overrides:formal field definitions / JSON examples / schema tables →L1rationale for protocol boundaries →L311.2 WRP v1.1 DAG Data Model & Compilation PipelineDefault document level:L2Typical chunk-level overrides:compilation algorithm pseudocode →L2concrete data structures / storage tables / code mapping →L1rationale for DAG compilation as separate phase →L311.3 WRP v1.2 Execution Traversal EngineDefault document level:L2Typical chunk-level overrides:ExecutionContext,ExecutionCursor,ExecutionReceiptstructures →L1orL2depending on specificitytraversal invariants / isolation rules →L2rationale for deterministic traversal and experimental modes →L311.4 WRP Migration PlanDefault document level:L3Reasoning:migration is a cross-cutting architectural transition strategy;the document explains sequencing, compatibility, and rollout discipline.Typical chunk-level overrides:actual migration tasks and repo changes →L1compatibility matrix / rollout constraints →L2migration philosophy and sequencing rationale →L312.
