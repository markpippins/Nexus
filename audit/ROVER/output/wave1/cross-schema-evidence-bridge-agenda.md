## 1. Cross-Schema Evidence Bridge v0.1 (evidence_links)
**Status:** `Agreed`

### Architectural Intent
Create a durable, queryable bridge between the knowledge schema (curated knowledge graph, "memories") and the nebula schema (harvested transcripts, "cabinet"). Right now the two schemas describe the same domain from different angles but have no cross-schema links.

### Requirements & Acceptance Criteria
- [ ] Current state: Two schemas adjacent but unlinked. Knowledge schema has graph_entities, graph_edges, graph_cross_references, graph_migrations, VECTOR(1536) + ivfflat index. Nebula schema has harvests_history, agent_records_history, cross_references, systems_history, requirements_history — no embeddings
- [ ] Same architectural decisions appear in both: "TypeSpec as executable knowledge layer" appears as a harvest candidate AND as a knowledge graph entity (typespec-dsl-layer). "3-tier graph model" appears as a knowledge graph `architectural_observation` AND in harvested specs
- [ ] New bridge table `knowledge.evidence_links`:
  ```sql
  knowledge.evidence_links
    id uuid pk
    knowledge_entity_id uuid NOT NULL
    nebula_harvest_id uuid NULL
    nebula_candidate_id uuid NULL
    link_type text NOT NULL  -- supports | refines | instantiates | contradicts | supersedes | mentions
    confidence numeric(5,4)
    provenance text
    created_at timestamptz
  ```
- [ ] Bridge lives in `knowledge`, not `nebula`, because this is a semantic interpretation of evidence, not a property of the harvest itself
- [ ] Link types: `supports`, `refines`, `instantiates`, `contradicts`, `supersedes`, `mentions`
- [ ] Must preserve provenance so you can safely rebuild or evolve the KG from harvest evidence later

## 2. Embedding Pipeline for Harvest Candidates v0.1
**Status:** `Agreed`

### Architectural Intent
Harvest candidates have rich intent_description text perfect for embedding, but no embedding generation pipeline exists. Add embedding generation and semantic indexing to the harvest pipeline so harvested content becomes searchable alongside the curated knowledge graph.

### Requirements & Acceptance Criteria
- [ ] Harvest candidates in `harvests_history.candidates` have `intent_description` fields — prime candidates for embedding
- [ ] Rover schema (`rover.chunks`) has `nlp_candidate_json` and `nlp_verdict` columns but those tables were never created in the production database
- [ ] Harvest source text is stored in `harvests_history.source_text` but never chunked, embedded, or indexed for semantic search
- [ ] Two options for embedding storage:
  - (a) Add vector column to nebula tables directly
  - (b) Embed in knowledge schema as a special entity type
- [ ] Embedding generation pipeline must be deterministic and re-runnable (not dependent on external API availability)
- [ ] Pipeline should produce chunks → embeddings → indexed for semantic_search() querying

### Harvested Code Artifacts
#### Purpose: Embedding pipeline gap analysis
```

  - Embedding generation (VECTOR(1536))
  - Semantic index for nebula data
Existing:
  - harvests_history.candidates with intent_description
  - knowledge.semantic_search() function (stub)
```

### Unresolved Follow-Ups

## 3. Source Provenance Bridge v0.1
**Status:** `Agreed`

### Architectural Intent
Create a bidirectional bridge between harvest candidates and the knowledge graph entities they inform. `knowledge.graph_entities.source_file` = `nexus-knowledge-graph.json`. `nebula.harvests_history.source_filename` = e.g., `Nexus - OrientDB, Pinecone & Convex.html`. The knowledge graph JSON has a `sources` array pointing to chat transcripts.

### Requirements & Acceptance Criteria
- [ ] Knowledge graph entities track `source_file` → `nexus-knowledge-graph.json`
- [ ] Nebula harvests track `source_filename` → the original chat transcript HTML file
- [ ] The knowledge graph JSON has a `sources` array pointing to chat transcripts — this is an implicit bridge
- [ ] A bidirectional query should let you go from: harvest candidate → the knowledge graph entities it informs AND from knowledge entity → the harvest candidates that support/refine/contradict it
- [ ] This bridge enables: tracing decisions back to their original evidence, validating knowledge graph entities against harvest data, rebuilding KG from evidence if needed

### Harvested Code Artifacts
#### Purpose: Source provenance chain
```
Chat transcript HTML → harvest candidate (nebula) → knowledge entity (knowledge) → system artifact
                                                      ↕
                                        evidence_links bridge table
```

### Unresolved Follow-Ups
- How to handle transcripts that don't have a matching knowledge graph entity?
- Should the `sources` array in the knowledge graph JSON be migrated into the evidence_links table?

## 4. Unified Semantic Search v0.1
**Status:** `Deferred`

### Architectural Intent
Once the evidence bridge and embedding pipeline exist, unify semantic search across both schemas. The `knowledge.semantic_search()` function exists but is a stub. It requires application-layer embedding generation before it can return results.

### Requirements & Acceptance Criteria
- [ ] Not the first move — build the evidence bridge and embedding pipeline first so search is grounded in provenance, not just similarity
- [ ] `knowledge.semantic_search()` function exists but is a stub (requires application-layer embedding generation)
- [ ] Once harvest candidates are embedded: "find all harvest candidates semantically related to 'TypeSpec contract-first architecture'" should return results from both the curated knowledge graph AND the automated harvest pipeline
- [ ] Cross-schema search must maintain provenance — returning results without the "why" is not sufficient
- [ ] Search results should include the evidence_links context when available (e.g., "this harvest candidate supports entity X")
