  # -------------------------------------------------
  # Pipeline configuration schema – one file per module
  # -------------------------------------------------
  $schema: "http://json-schema.org/draft-07/schema#"
  title: "ModulePipelineConfig"
  type: object
  properties:
    pipelineName:
      type: string
      description: Logical name of the pipeline that will operate on this
  module.
    emitEnabled:
      type: boolean
      description: |
        `true`  – module will emit work‑requests (default).
        `false` – module only receives work‑requests; emitter becomes a no‑op.
      default: true
    worktree:
      type: boolean
      description: |
        `true`  – create an isolated git worktree before making changes.
        `false` – work directly in the current checkout.
      default: false
  required:
    - pipelineName
  additionalProperties: false

  How to use it

  - Add a file <module‑root>/.pipeline/pipeline-config.yaml that conforms to
  this schema.
  - Example for jvm/spring (consumer‑only):

  pipelineName: spring-workflow
  emitEnabled: false
  worktree: true

  Why this helps

  - Provides a machine‑readable contract that the pipeline‑setup skill can parse
   and act on.
  - Makes the intent of the module explicit, removing guesswork.

  import java.util.Map;
  import java.util.logging.Logger;

  /**
   * Utility used by the work‑request pipeline.
   *
   * In *producer* modules this class writes a JSON file to
   * <repo‑root>/work_requests/.  In *consumer* modules (emitEnabled:false)
   * the {@code emit} method becomes a no‑op that only logs the call.
   *
   * The class is deliberately tiny so that it can be compiled into any
   * module without pulling in additional dependencies.
   */
  public final class WorkRequestEmitter {

      private static final Logger LOG =
  Logger.getLogger(WorkRequestEmitter.class.getName());

      private WorkRequestEmitter() { /* utility class */ }

      /**
       * Emit a work request.
       *
       * @param type    logical request type, e.g. "SERVICE_UPDATE"
       * @param payload arbitrary map that will be serialized to JSON
       */
      public static void emit(String type, Map<String, Object> payload) {
          // The actual implementation will be replaced at build time
          // by the pipeline‑setup script if emitEnabled == true.
          LOG.fine(() -> String.format("WorkRequest emit called (no‑op) –
  type=%s, payload=%s", type, payload));
      }
  }

  The build script generated by pipeline‑setup will overwrite the body of emit
  with real file‑write logic when emitEnabled:true. When false, the stub stays
  in place.

  Why this helps

  - Guarantees that every module contains a WorkRequestEmitter class,
  eliminating the “do I need to add one?” question.
  - The stub version is safe for consumer‑only modules, so developers can import
   it without side effects.

  ## Using Work‑Requests as a *Target* (consumer‑only)

  Some projects – for example the `jvm/spring` suite – are updated **by** a
  pipeline rather than generating work‑requests themselves.  To mark a module as
  such:

  1. Create `<module>/.pipeline/pipeline-config.yaml` with `emitEnabled: false`.
  2. Run the `pipeline‑setup` skill (or the `superpowers:writing-plans` flow) –
     it will generate a stub `WorkRequestEmitter` that does nothing.
  3. The orchestrator will still invoke the module’s pipeline when a request
     arrives, but the module will never emit its own requests.

  This pattern avoids accidental emission code and makes the module’s role
  explicit to future contributors.

  Why this helps

  - Puts the concept of a “target‑only” module in the same place developers
  already look for work‑request semantics.
  - Provides a clear, step‑by‑step recipe that can be copied verbatim.
