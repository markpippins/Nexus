# File Ingest v2 -- Architecture Plan

## Goal

An **event-driven, file-agnostic observation and acquisition subsystem**. It walks filesystems, classifies what it finds, extracts structured metadata through pluggable handlers, and emits immutable events that downstream subsystems (event-pipeline, semantic layers, governance) consume. The system produces **observations**, not conclusions. It is intentionally epistemically conservative.

---

## 1. Design Principles

| Principle | Meaning |
|---|---|
| **Event-centric** | The event store is the system of record. MySQL registries and MongoDB documents are materialized projections, not canonical truth |
| **Observation over conclusion** | The system reports what it observed, not what it "understands." Semantic interpretation belongs to downstream layers |
| **Registry-driven** | File types, handlers, encodings, matchers, directory types are rows in MySQL, not enums in Python |
| **Encoding-aware** | Metadata schemas differ by encoding. Handlers declare which encodings they support |
| **Provenance-attached** | Every extracted attribute carries handler identity, extraction timestamp, and confidence. You can always answer "why does the system believe this?" |
| **Confidence-scored** | Classifications, extractions, matches, and directory type inferences are probabilistic signals, not binary assertions |
| **Asset identity != path** | Content hash is the canonical asset identity. Paths are observations recorded at a point in time. An asset can appear at multiple paths over time; a path can host different assets |
| **Resolution is evented** | Duplicate resolution goes through a lifecycle (proposed, approved, reverted, contested, expired), not a one-time final state |
| **Resumable execution** | All long-running operations checkpoint to Redis for resume after restart |

### 2.2 Technology Stack

| Layer | Technology | Purpose |
|---|---|---|
| API | FastAPI (Python) | HTTP API for UI and external consumers |
| Event Store | MySQL | Immutable event log + registry tables + matcher config |
| Read Models | MongoDB | File + directory metadata projections (flexible, queryable) |

### 2.3 Key Architectural Decision

**The event store (MySQL) is the system of record.** The MongoDB collections are *materialized projections* rebuilt from events. If MongoDB is lost, it can be regenerated by replaying the event log. The pipeline does NOT write to MongoDB as its final step -- it emits an event, and a projection handler updates MongoDB asynchronously.

This also means downstream systems (event-pipeline, html-importer) consume from the event log, not from MongoDB. They subscribe to event types they care about (e.g., `FileObserved{file_type: html}` triggers the html-importer's transcript parser).

## 3. Event Model

Every state change in the system is recorded as an immutable event with a common envelope.

### 3.1 Common Envelope

| Field | Type | Description |
|---|---|---|
| `id` | VARCHAR(36) | UUID |
| `event_type` | VARCHAR(64) | Discriminator |
| `timestamp` | DATETIME(6) | When the event occurred |
| `recorded_at` | DATETIME(6) | When the event was persisted |
| `source` | VARCHAR(64) | `scanner`, `handler:{name}`, `matcher:{name}`, `resolver`, `human` |
| `scan_session_id` | VARCHAR(36) | Which scan produced this event (nullable) |
| `content_hash` | VARCHAR(64) | Content hash of the asset this event refers to (nullable) |
| `payload` | JSON | Type-specific data |
| `provenance_hash` | VARCHAR(64) | SHA-256 of payload for integrity verification |

### 3.2 Downstream Integration

Events are consumed by `event-pipeline` and `html-importer` via the `sequence` column (offset-based consumption). The envelope is intentionally simpler than the `IR_v2_EventEnvelope` used in html-importer -- it does not include execution universes, determinism hashes, or policy references. The consuming layer is responsible for wrapping ingest events into its own IR model.

### 3.3 Event Type Catalog

#### Discovery & Observation

| Event | Source | Payload |
|---|---|---|
| `ScanStarted` | scanner | `{library_id, path, deep_scan}` |
| `ScanCompleted` | scanner | `{library_id, path, files_processed, error_counts}` |
| `ScanFailed` | scanner | `{library_id, path, error, files_processed}` |
| `DirectoryObserved` | scanner | `{path, stat, parent_path, file_count}` |
| `FileObserved` | scanner | `{path, stat, content_hash, mime_guess, observation_time}` |

#### Classification

| Event | Source | Payload |
|---|---|---|
| `FileClassified` | classifier | `{content_hash, file_type, encoding, mime_type, category, confidence}` |
| `DirectoryClassified` | classifier | `{path, type_signals: [{type_name, confidence}, ...], matched_pattern}` |

`DirectoryClassified.type_signals` is a list, not a single authoritative assignment. Multiple directory types may be inferred for the same directory with different confidence levels. Downstream systems decide which interpretation to use.

#### Metadata Extraction

| Event | Source | Payload |
|---|---|---|
| `MetadataExtracted` | handler:{name} | `{content_hash, encoding, attributes: [{name, value, confidence, handler_name}], duration_ms}` |
| `MetadataExtractionFailed` | handler:{name} | `{content_hash, handler_name, error_type, error_message}` |
| `HandlerNotApplicable` | handler:{name} | `{content_hash, file_type, encoding, reason}` |

Each attribute in `MetadataExtracted` carries its own provenance: which handler extracted it, and with what confidence. This allows downstream to weigh conflicting extractions (e.g., ID3v1 says artist=X with confidence 0.5, ID3v2 says artist=Y with confidence 0.9).

#### Identity & Relationships

| Event | Source | Payload |
|---|---|---|
| `AssetCanonicalized` | resolver | `{content_hash, canonical_path, aliases: [...]}` |
| `PathObserved` | scanner | `{content_hash, path, observation_time, mount_point}` |

`PathObserved` is the mechanism that decouples identity from location. An asset (identified by content_hash) can appear at multiple paths over time. Each observation is a separate event. When a file is deleted or moved, the old path shows a newer `PathObserved` for a different content_hash (or none).

#### Matching & Resolution

| Event | Source | Payload |
|---|---|---|
| `MatchDetected` | matcher:{name} | `{content_hash_a, content_hash_b, matcher_name, score, max_score, comparison}` |
| `ResolutionProposed` | resolver | `{match_id, action: keep|delete|mark, rationale, confidence}` |
| `ResolutionApproved` | human | `{resolution_id, approved_by}` |
| `ResolutionRejected` | human | `{resolution_id, rejected_by, reason}` |
| `ResolutionExecuted` | resolver | `{resolution_id, action_taken, files_deleted}` |
| `ResolutionReverted` | human/system | `{resolution_id, reason}` |

#### Error & Governance

| Event | Source | Payload |
|---|---|---|
| `PipelineError` | scanner | `{phase, content_hash, error_type, error_message}` |
| `PolicyViolationDetected` | resolver | `{policy_name, content_hash, violation_detail}` |

## 5. Data Model (MongoDB -- Read Projections)

MongoDB documents are **materialized views** rebuilt from events. They exist for query performance and flexible schema, but they are not the system of record.

### 5.2 Directory Metadata Projection (`directory_metadata`)

Built from `DirectoryObserved` + `DirectoryClassified` events.

```json
{
  "_id": "ObjectId",
  "absolute_path": "/media/music/albums/Artist - Album",
  "directory_name": "Artist - Album",
  "parent_path": "/media/music/albums",
  "type_signals": [
    {"type_name": "album", "confidence": 0.82, "source": "pattern_match:/albums"},
    {"type_name": "artist", "confidence": 0.45, "source": "name_heuristic"}

  "primary_type": "album",
  "primary_confidence": 0.82,
  "amelioration_applied": null,
  "file_count": 12,
  "total_size": 524288000,
  "last_event_sequence": 982,
  "scanned_at": "2024-06-01T12:00:00Z"

```

Key design: `type_signals` is an array of scored inferences, not a single authoritative type. The `primary_type` field is a convenience for querying (the highest-confidence signal). Downstream systems can use the full signal list for richer interpretation.

## 6. Pipeline Architecture

### 6.1 Pipeline Flow

```
+-----------+     +----------------+     +-----------+
| Discovery | --> | Classification | --> | Handling  |
| (scanner) |     | (classifier)   |     | (handlers)|
+-----+-----+     +-------+--------+     +-----+-----+
      |                     |                    |
      v                     v                    v
  +---------------------------------------------------+
  |              Event Store (ingest_event)            |
  +---------------------------------------------------+
                           |
                           v
  +---------------------------------------------------+
  |          Projection Handler (async)                |
  |  rebuilds MongoDB read models from events          |
  +---------------------------------------------------+
                           |
                           v
  +---------------------------------------------------+
  |              Matching Engine (async)               |
  |  triggered on MetadataExtracted events             |
  +---------------------------------------------------+
                           |
                           v
  +---------------------------------------------------+
  |              Resolution (async)                    |
  |  triggered on MatchDetected events                 |
  +---------------------------------------------------+
```

### 6.2 Discovery Phase

1. Load `library_paths` where `scan_enabled = true`
2. Walk each path with `os.walk()`, building file queue
3. Emit `DirectoryObserved` for each directory
4. Compute content hash (SHA-256) for each file
5. Emit `FileObserved` with stat, hash, and mime guess
6. Checkpoint queue to Redis for resumability
7. Emit `ScanStarted` / `ScanCompleted` / `ScanFailed` at boundaries

### 6.3 Classification Phase

For each `FileObserved` payload:
1. Look up extension in `file_type` registry
2. Detect encoding via magic bytes / header inspection
3. Look up applicable handlers from `file_handler_registration`
4. Emit `FileClassified` with type, encoding, confidence
5. For directories: run pattern matching, emit `DirectoryClassified` with type signals

### 6.4 Handling Phase

For each classified file:
1. Select highest-priority active handler matching the file type + encoding
2. Handler extracts attributes using the `file_attribute` registry as a guide
3. Each attribute is extracted with its own confidence score
4. Emit `MetadataExtracted` with provenance per attribute
5. If handler fails: emit `MetadataExtractionFailed`, fall back to next handler
6. If no handler applies: emit `HandlerNotApplicable`, file gets basic metadata only
7. Generic handler always runs as final fallback

### 6.5 Projection Phase (Async)

Triggered by events, runs in background:
1. `FileObserved` -> upsert skeleton in `file_metadata`
2. `FileClassified` -> update type/encoding/confidence fields
3. `MetadataExtracted` -> merge attributes with provenance into `file_metadata`
4. `AssetCanonicalized` -> update canonical_path
5. `PathObserved` -> append to `observed_paths` array
6. `DirectoryObserved` -> upsert `directory_metadata`
7. `DirectoryClassified` -> update `type_signals` array

### 6.6 Matching Phase (Async)

Triggered on `MetadataExtracted` events. Batched and debounced:
1. For each active `matcher` config:
   - Build query from `matcher_field` entries
   - Search across the `file_metadata` projection for matches
   - Score candidate pairs
2. Emit `MatchDetected` for pairs exceeding threshold
3. Projection handler updates `match_record` table

### 6.7 Resolution Phase (Async + Human)

1. ResolutionProposed generated by rules engine evaluating match records
2. Human approves or rejects via API
3. If approved: emit ResolutionExecuted (delete lower-quality file)
4. Resolution can be reverted: emit ResolutionReverted
5. Resolution status tracked in match_record.updated_at

## 7. Handler Plugin Interface

All handlers implement:

```python
class BaseHandler(ABC):
    name: str                       # From registry
    supported_encodings: List[str]   # e.g. ["id3v2", "vorbis_comment"]

    async def can_handle(self, file_path: str) -> bool: ...

    async def detect_encoding(self, file_path: str) -> Optional[str]: ...

    async def extract_attributes(
        self,
        file_path: str,
        encoding: str,
        requested_attributes: List[str]  # From file_attribute registry
    ) -> List[ExtractedAttribute]: ...
```

Where `ExtractedAttribute` is:

```python
@dataclass
class ExtractedAttribute:
    name: str
    value: Any
    confidence: float         # 0.0 - 1.0
    handler_name: str
```

Handlers are loaded dynamically at startup from the `file_handler` registry. No hardcoded imports.

## 8. Event Emission Protocol

The pipeline emits events to the `ingest_event` table. Every event has a common envelope. The table uses a `BIGINT AUTO_INCREMENT` sequence column for offset-based consumption.

Consumers (event-pipeline, html-importer) read events via:

```
SELECT * FROM ingest_event
WHERE sequence > :last_processed_sequence
ORDER BY sequence ASC
LIMIT 100
```

Or filter by type:

```
SELECT * FROM ingest_event
WHERE event_type = 'FileObserved'
  AND sequence > :last_processed_sequence
  AND JSON_EXTRACT(payload, '$.file_type') = 'html'
ORDER BY sequence ASC
```

## 13. What This System Is NOT

- It does NOT perform semantic interpretation of content
- It does NOT build a knowledge graph
- It does NOT extract entities, topics, or sentiment
- It does NOT make governance decisions
- It does NOT orchestrate downstream workflows

It is an **acquisition and normalization subsystem**. It observes, fingerprints, classifies, extracts structured attributes, and emits facts. Downstream layers (event-pipeline for orchestration, html-importer for semantic analysis of transcripts, governance for policy enforcement) consume those facts and do the heavy cognitive lifting.

The contract: **ingest-v2 produces evidence. Everything else produces understanding.**

## 14. Open Questions

1. **Event store retention**: How long do we keep events? Indefinitely? With a compaction policy? This affects storage sizing and replay time.

2. **Projection consistency**: Should the projection handler be synchronous (update MongoDB within the same transaction as event write) or async (eventual consistency)? Async is simpler but introduces a delay before query results reflect the latest scan.

3. **Matching engine backends**: The matcher config has must/should/must_not semantics. Do we implement against MongoDB aggregation (field-level only), or bring in a lightweight search library (Whoosh, Tantivy) for text matching with boosts? MongoDB text search does not support field-level boosting natively.

4. **Encoding detection granularity**: Should encoding detection happen *before* handler dispatch (a separate encoding detector module) or *inside* each handler's `detect_encoding` method? The former is more modular; the latter lets handlers use format-specific heuristics.

5. **Confidence propagation**: When multiple handlers extract the same attribute with different confidence scores, how do we merge them in the projection? Last-write-wins? Highest-confidence-wins? Weighted blend? This is a projection concern, not an event concern -- the events preserve all raw extractions.

6. **Content hash strategy for large files**: Computing SHA-256 for every file during scanning is I/O-intensive. Should we use a sampling strategy (first N KB + last N KB) for large files, reserving full-hash for files flagged as potential duplicates?
