Kernel vs Projection: WRP Reduce Design Analysis

1. The Core Distinction

The WRP Kernel Reduce spec (Spec 2) defines a generic state machine:

function Reduce(state: KernelState, ir: LOSMIR): KernelState

type KernelState = {
  plans: Map<PlanId, PlanState>;
  receipts: Map<ReceiptId, ReceiptState>;
  transitions: TransitionLog[];
  references: GraphIndex;
  version: number;
};

The existing conduit_wrp_reducer.py builds a projection, not kernel state:

WRPProjectionBuilder.reduce(plan_id, title, project, ..., receipts) -> WRPProjection

type WRPProjection = {
  planId: string;
  wrpState: WRPState;
  stateHistory: WRPEvent[];
  abstractionLevel: AbstractionLevel;
  chunks: StratifiedChunk[];
  crossReferences: CrossReference[];
  ...
};

Key insight: A projection is a view derived from kernel state. The kernel is the source. Currently there is no kernel — only projection builders that reconstruct state from raw receipts every time.

2. Architectural Analysis

Existing code is already a partial kernel implementation

The existing conduit receipt pipeline already implements three of four Reduce phases:

  • Receipt Materialization (Phase 1): Receipts are stored in SQLite/PostgreSQL with sequence, type, agent_role, etc.
  • Plan State Construction (Phase 2): WRPProjectionBuilder.reduce() folds receipts into a WRPState per plan
  • Transition Application (Phase 3): The adjacency matrix validates transitions; invalid ones are silently skipped
  • Graph Index Update (Phase 4): NOT IMPLEMENTED — no cross-plan reference graph exists

What the spec adds that doesn't exist

  • Multi-plan KernelState: Currently one plan at a time. Spec says Map<PlanId, PlanState> — all plans in one state machine.
  • GraphIndex: Cross-plan reference graph. The crossref_taxonomy.py defines 14 relation types but no graph structure exists.
  • Version progression: state.version increments on each state-modifying IR.
  • All-or-nothing semantics: Current code uses convergence (skip invalid). Spec says if any phase fails, no state change.
  • LOSMIR as explicit input: Spec says Reduce takes LOSMIR. Current code takes raw receipt lists.
  • TransitionLog[]: No explicit transition log in kernel state (though stateHistory exists in the projection).

3. Design Tensions

Tension 1: All-or-nothing vs Convergence

All-or-nothing (spec): If any transition is invalid, entire IR snapshot is rejected. State unchanged. Safer but fragile.

Convergence (existing): Invalid transitions are silently skipped. State stays at last valid position. Resilient but can lose events silently.

Decision: For a kernel, all-or-nothing is architecturally correct — the calling layer decides how to handle rejection. For the projection builder, convergence is pragmatically useful. These can coexist if the kernel enforces strictness while the projection layer handles tolerance.

Tension 2: Single-plan vs Multi-plan KernelState

The spec says KernelState holds ALL plans. The existing code processes ONE plan at a time. A multi-plan kernel could detect cross-plan conflicts, enable the GraphIndex, and support temporal queries across plans. But it's more complex and requires loading all plans into memory.

Decision: The kernel should operate on a per-plan basis internally (each Reduce invocation processes one plan's IR), but KernelState can hold multiple plans as a composite. This matches event sourcing: each event affects one aggregate, but the store holds all aggregates.

Tension 3: What is LOSMIR?

In the existing code, "LOSMIR" is a type system (losm-ir package) with WorkRequestDCO, PlanIR, SpecIR, ExecutionIR, ExecutionReceipt, etc. As kernel input, LOSMIR could be:

  • A stream of Receipts (simplest — existing code already handles this)
  • A WorkRequestDAG (richer — includes step dependencies and structure)
  • An IRDeltaStream (from Spec 4 — but doesn't exist yet)

Decision: Start with Receipt streams as the kernel input type. This maps cleanly to the existing conduit pipeline. Spec 4 (IRDeltaStream) can be implemented on top later as a richer input format.

Tension 4: GraphIndex structure

The spec says KernelState has references: GraphIndex. The available data is the crossref_taxonomy (14 types: wrp:depends_on, wrp:supersedes, ag:references_plan, kv:sourced_from, etc.). A GraphIndex could be:

  • Adjacency list: Map<string, CrossReference[]> — simple but no traversal
  • Property graph: Nodes with typed edges — supports k-hop traversal
  • Separate index: A read-optimized structure built after phases 1-3

Decision: The GraphIndex should be a simple adjacency list initially: Map<string, List<{relType, targetId, metadata}>>. This supports the Temporal Query Model (Spec 6) GraphSelector traversal. It can be enriched later.

4. Proposed Architecture: Two-Layer Reduce

Resolve the tensions by defining two layers:

Layer 1: Kernel Reduce (strict, generic)

function Reduce(state: KernelState, ir: LOSMIR) -> KernelState

// 4 explicit phases, all-or-nothing
// Pure function, no IO, no side effects
// Holds cross-plan GraphIndex
// Map<PlanId, PlanState> with version tracking

Layer 2: Projection Builder (derived, pragamatic)

function BuildProjection(kernelState, planId, options) -> WRPProjection

// Extracts one plan's view from KernelState
// Applies stratification, chunk building, cross-ref filtering
// Convergence semantics for display purposes
// Disposable — can be rebuilt from kernel state at any time

Connection to existing code

  • Existing WRPProjectionBuilder.reduce() → becomes BuildProjection()
  • New module wrp_kernel.py → implements Reduce()
  • The existing reducer converges on invalid transitions; the kernel rejects them
  • The kernel holds Map<PlanId, PlanState>; each Reduce() invocation affects one plan
  • GraphIndex is built during Phase 4 by scanning cross-plan references

5. Implementation Strategy

Phase 1: wrp_kernel.py — KernelState + Reduce()

  • New pure Python module in nexus/python/conduit/wrp_kernel.py
  • KernelState dataclass with plans, receipts, transitions, references, version
  • Reduce() with 4 explicit phase methods: _materialize(), _construct(), _apply(), _updateGraph()
  • All-or-nothing: if any phase raises, KernelState is unchanged
  • LOSMIR input = List[ConduitReceipt] initially (upgradable to IRDeltaStream later)
  • GraphIndex = simple adjacency map built from crossref_taxonomy types

Phase 2: Refactor WRPProjectionBuilder on top of KernelState

  • Existing WRPProjectionBuilder.reduce() becomes a projection over KernelState
  • Keeps convergence semantics for the projection layer
  • Stratification, chunk building, cross-ref building unchanged

Phase 3: Temporal Query Model (Spec 6) on top

  • WRPQuery type with 5 selectors
  • Query execution resolves branch, replays kernel state, executes selector
  • Projection = Query(WRPQuery)

6. Open Questions for Implementation

  • Persistence: Is KernelState in-memory only, or persisted to SQLite? If persisted, do we snapshot KernelState or replay from receipts on restart?
  • Concurrent access: Does the kernel need to handle concurrent Reduce() calls? If so, locking or immutable versioning?
  • LOSMIR schema versioning: What happens when the LOSMIR type schema evolves? Kernel version field?
  • GraphIndex traversal: Does the GraphIndex support the GraphSelector's depth parameter from Spec 6? k-hop or just direct edges?
  • Error reporting: How does the kernel communicate which phase failed and why? Return type: KernelState | KernelError?
